# 1-hive deployment

Everything needed to rebuild 1-hive's record. Secrets and private keys live in `~/.config/hive/`, never here.

The services run from two shared repositories, each installed by `up.sh` as a clean checkout at the tag pinned in `hive.env` (`HIVE_RUNTIME_REF`, `HIVE_BRIDGE_REF`), in `~/.local/share/1-hive/`. 1-hive uses their defaults, so it sets none of their settings:
- [hive-runtime](https://github.com/1-hive/hive-runtime): the launcher, dispatcher, supervisor, sweeper, the chief of staff's tools (`cos.sh`, `hive-mcp.py`), agent ports, agents' git access (`git/`), the agent image (`agent/`), agent users (`agent-users.sh`, run once with sudo: one OS user per agent actor, plus the sudoers rule for `/usr/local/bin/hive-agent-podman`) and `op`. `up.sh` links `~/.local/bin/op` to it and runs its `git/install.sh`.
- [hive-bridge](https://github.com/1-hive/hive-bridge): the Telegram bridge, `telegram-say.py` and the Floor.

To move to a new version: tag it there, change the ref in `hive.env`, run `up.sh`.

| File | What |
|---|---|
| `hive.env` | Settings: hive id, profile, mode, ports, the hive-record version, the operator's **public** key |
| `registry.json` | hivepin repository registry: hive-record (policy), the workspace, mtg-player |
| `compose.yml` | The record's Postgres (container `1hive-pg`, loopback port 5433) |
| `actors.json` | The agent actors, with **public** keys only |
| `up.sh` | Bring 1-hive up; every step is skipped when already done. Enables `podman-restart` so the databases (`restart: always`) return after a reboot; the gateway retries every 5 s until its database is up; `~/.config/environment.d/999-1hive-path.conf` puts `~/.local/bin` on user services' PATH |
| `register-actors.sh` | Register new actors from `actors.json`. Run by the operator; signs with `~/.config/hive/operator.key` |
| `apply-policy.sh [reason]` | Move the running hive to the policy at `HIVE_RECORD_REF` with a recorded `hive.policy_changed`. Run by the operator |
| `route-table.yaml`, `route-sources.yaml` | The router's table (routes, pools, tiers, and since v17 `subagents`: Opus attempts may hand well-specified subtasks to Sonnet on the same plan, hive-route §4.9) and its sources (usage readers, harness commands, the qualifications file). The launcher writes each attempt's subagents as `.claude/agents/route-<id>.md` in the task folder and tells the worker about them in `KICKOFF.md` |
| `~/.config/hive/route-overrides.json` (not in git) | The operator's standing route overrides (RT1) for workers, per task or goal: `{"tasks": {...}, "goals": {"<goal>": {"route_id", "reason", "by": "operator"}}}`. The launcher applies them to workers. `reviews` (same shape) is the review fallback: used only when the router can't route a review now (`wait` or `no_route`, e.g. Codex out of credits), so a same-family review happens only with the operator's standing consent. `opus-max` (Opus 5.5, max effort) is in no tier, so only an override picks it |
| `review-allowlist.json` | Claude Code permissions for the `claude-code-allowlist` harness (`--permission-mode dontAsk`): what a reviewer on a self-hosted route may do, with no model judging its actions. Not a sandbox: `python3` and `podman` reach what the OS user can. Image reads are denied: the routes on this harness are text-only, and an image ends the attempt with an API error |
| `apply-registry.sh [reason]` | Move the running hive to `registry.json` (e.g. a newly registered repository) with a recorded `hive.registry_changed`, and restart the gateway to load it. Run by the operator |
| `runtime` | Where agents run by default: `host` or `container` (hive-runtime's `launch-task.sh`, `ROUTE_RUNTIME` overrides) |
| `reset.sh --yes-destroy-the-log` | Start fresh: archive the log to `~/.local/share/1-hive/archive/`, destroy the database, run `up.sh`. Git repositories are untouched |
| `backup.sh` | One backup now; `up.sh` installs the `1-hive-backup` timer, daily at 03:30 local. Each dated folder in `~/.local/share/1-hive/backups/` holds `record.jsonl` (the log, re-verified; `hive restore`), a git bundle of every local remote in `~/repos/*.git` (`git clone --mirror`), and `config.tar` (keys and secrets, mode 600). Keeps 14. **Same disk only** until `HIVE_BACKUP_REMOTE` (an rsync target on another machine) is set in `hive.env` |
| hive-runtime's `sweeper.py [--dry-run]` | Run daily at 04:00 by the `1-hive-sweeper` timer (`up.sh`). Removes a task folder (`~/work/1hive/<task>`, `<task>-review`) once its task is done or cancelled, its goal accepted or abandoned 3 days ago (`--grace-days`), every commit its results pin is in its hub repository, nothing running uses it, and it has no `KEEP` file at its top. Agent-owned files go through each agent user's `podman unshare`. Then prunes agent users' stopped containers and images older than 3 days. Removals go to `~/work/1hive/.sweeper/log.jsonl`, and the daily digest says how much was freed. `--dry-run` lists each folder and why it stays or goes |
| `../tools/watchdog.py [--dry-run]` | Run every 2 minutes by the `1-hive-watchdog` timer (`up.sh`). Checks the record's Postgres containers, the gateway's health, that every 1-hive service is active and that the backup and sweep jobs didn't fail. A problem seen on two checks in a row goes to the operator's Telegram (directly, so it works with the bridge down), and "all clear" follows once it's fixed. `--dry-run` prints the checks without sending |

The gateway runs as the user service `1-hive-gateway.service` on `http://127.0.0.1:8470`. The supervisor (hive-runtime's `supervisor.py`) runs as `1-hive-supervisor.service`: it nudges silent workers, restarts dead or stalled ones with context generated from the record, and escalates to the chief of staff. A reviewer that ends without a verdict on a usage or quota limit (e.g. "out of credits") isn't escalated: the dispatcher relaunches it. Three kinds of escalation go to the operator instead, as interrupts (PLAN D15): a task that fails repeatedly (`repeated_failure`), a result whose reviewer hit a usage limit three times (`other`), and an active goal past its budget (`goal.escalated`, `budget_exceeded`; wall clock counts from approval). Everything it does is recorded under the actor `supervisor`. Logs: `journalctl --user -u 1-hive-supervisor`.

The dispatcher (hive-runtime's `dispatcher.py`) runs as `1-hive-dispatcher.service`, as actor `dispatcher` (class coordinator, its own key). It starts every agent the record calls for, with kickoffs written from the record:
- **Workers.** A task assigned to a worker is launched once, with no attempt by hand. A blocked task answered since its block (`task.answered`) is relaunched once to read the answer and continue; restarts stay with the supervisor.
- **Reviews.** When a task's current result has no reviewer, it emits `review.assigned` and launches the reviewer. It tries `reviewer.codex.1` first, then `reviewer.claude.1`, never the result's author. If the router has no route for either, it retries every 10 minutes. An assigned reviewer whose launch failed, or whose process hit a usage limit, is relaunched (`ROUTE_LAST_CLASS=capacity`): the launcher holds that pool for the task until the provider's reset, or for an hour when none is known (`ROUTE_CAPACITY_HOLD`), so the router picks another pool or waits. Closing a reviewed task stays with the chief of staff. Logs: `journalctl --user -u 1-hive-dispatcher`.

The Telegram bridge (hive-bridge's `telegram-bridge.py`) runs as `1-hive-telegram.service`. Free text goes to the chief of staff (`cos.sh chat`) on its own thread, one message at a time, stopped after 15 minutes; buttons keep working meanwhile. Each `goal.approved` (Telegram or `op`), each escalation to the chief of staff, each blocked task (a worker's question) and each passed review is passed to it as a chat message, so it acts unprompted; its reply reaches you in the chat, unless it says nothing ("No response requested."). When you ask it to check something later, it leaves a follow-up in `~/work/1hive/cos/followups/` and the bridge wakes it then; only follow-ups written while it answers you count (within 16 minutes of your message, at most 2 hours ahead, 3 pending). An over-budget alert has a **+4h** button; `op budget <goal> <hours>` does the same from the host. A reply may carry pictures or files (`[[photo: path]]`, `[[file: path]]` on a line of their own), only from the chief of staff's workspace clone, at most 5 per reply, 10 MB each. The digest lists results waiting over an hour for a review verdict, with what the review is doing, and the chief of staff's open requests (`hive-requests/` on the workspace's main, not yet in `done/`). It pushes the operator's inbox: goals to approve or accept, and escalations to the operator. It also sends a **daily digest at 08:00 local time** (`--digest-at`), and `/digest` sends one on request. Each digest names the time of the next one, so a digest that doesn't arrive is the alarm. When a task is done (closed or cancelled), a one-line note comes without buttons (`--no-feed` turns them off). Logs: `journalctl --user -u 1-hive-telegram`. `/board` there lists open goals and tasks with what each agent is doing now, from the Floor. hive-runtime's `telegram-say.py "text"` sends you one plain message in the same chat from the host (the operator's host sessions, while you are away); a reply goes to the chief of staff.

The Floor (hive-bridge's `floor.py`, page `floor/index.html`) runs as `1-hive-floor.service` on `http://127.0.0.1:8476`: a read-only live board. Goals as lanes with their wall-clock budget, tasks moving through queued, working, in review and closed, and the record as a strip of cells, one per event, that you drag to see the board at any position (the gateway's own fold, `GET /v1/state?at=`). It reads the record as actor `floor` (class instrument, its own key `~/.config/hive/floor.key`), which never emits. What each agent is doing (last tool call, activity in the last hour, quiet time, model, a task in review whose reviewer never started) comes from each attempt's log in its task folder (`worker-N.jsonl`, `review-N.jsonl`, `codex-N.log`) and `.route/<task>/*.attempt.json`; it is never authoritative. Loopback only: on the phone, use `/board`. Logs: `journalctl --user -u 1-hive-floor`.

**Container runtime** (PLAN Phase E 1; the default since 2026-10-06, goal `container-pilot`). With `runtime` set to `container`, each attempt runs in its own rootless Podman container (`hive-<task>-<role>-<n>`, removed when it ends). The container gets:
- the task's folder, at the same path;
- this actor's record key and git key, read-only;
- the harness's credentials. For Claude Code this is `~/.config/hive/claude-oauth-token`, made with `claude setup-token`, never the operator's own login. For Codex it is the shared `~/.codex` login.

It has no route to the host's loopback: the record, the model gateway and sshd reach it through Unix sockets (hive-runtime's `agent-ports.py`, user service `1-hive-agent-ports`, in `~/work/1hive/.ports`, which only group `hive` may enter). The image's `hive-entry` relays them to the same ports on the container's own loopback. Nothing else on the host is reachable, the record's Postgres included. Git goes over SSH as the actor: hive-runtime's `git/hive-git-shell` is the key's forced command, and the repositories' `pre-receive` hook lets agents create or fast-forward only `hive/*` branches and the workspace's `main`. No deletions, rewrites or tags. The agent runs as container root, which is the operator's user on the host, so it can run nested Podman for games. That includes bridge networks like the human-play sandbox's, which need `NET_ADMIN` and `SYS_ADMIN` over the container's own namespaces; rootless, these give nothing beyond the operator's user on the host. The supervisor stops a container by name (`podman stop`). One-time operator setup: hive-runtime's `git/install.sh` (hooks, per-agent SSH keys in `authorized_keys`), hive-runtime's `agent/build.sh`, `claude setup-token` saved to `~/.config/hive/claude-oauth-token`.

**Agent users** (hive-runtime's `agent-users.sh`, since 2026-10-06). Each actor has its own OS user (`hive-worker-claude-1`, …), and its containers run in that user's rootless Podman (`sudo -u <user> /usr/local/bin/hive-agent-podman`). An agent that escapes its container is that unprivileged user: it can't read the operator's files, other agents' keys or other tasks' folders. In detail:
- **Keys and settings** reach the container as that user's Podman secrets, per attempt: the record key, the git key, `known_hosts`, the review allow-list, and the Claude token.
- **Task folders:** the launcher grants the user only that task's folder (ACLs, which keep the operator's access too).
- **Codex:** each actor the router may send to Codex needs its own login, once: `reviewer.codex.1`, and also `worker.claude.1`, since the router moves work to the ChatGPT pool when the Claude pool is above its soft threshold (hive-route RT6). As the operator, create the folder (`sudo -u hive-worker-claude-1 /usr/local/bin/hive-agent-podman unshare mkdir -p /var/lib/1hive-agents/hive-worker-claude-1/.codex`), then run `sudo -u hive-worker-claude-1 /usr/local/bin/hive-agent-podman run --rm -it --network host -v /var/lib/1hive-agents/hive-worker-claude-1/.codex:/root/.codex localhost/1hive-agent:latest codex login --device-auth`, and open the URL it prints. If the browser ends on a `http://localhost:1455/auth/callback?...` page (a remote browser can't reach this host's loopback), run `curl -s "<that address>"` on the host while the login is still waiting. A token exchange that times out can just be retried.
  - If the browser is on another device, the final redirect to `localhost:1455` fails there. Copy that whole address and run `curl '<address>'` on this machine while the login waits. Keep the quotes, so `&state=` survives.
  - Use `codex login --device-auth` instead if the account allows device codes.
- **The image** is copied into each user's storage when it changes.

Without an agent user, the launcher falls back to the operator's Podman and the operator's Codex login.

**Route facts.** Every work order states its task's facts on a line of its own, which hive-runtime's `launch-task.sh` passes to the router: `Route facts: specification=explicit verification=independent scope=few consequence=reversible leverage=0`. Any fact may be `unknown` (it then takes the costly default). A new task whose order has no such line is refused at launch (`ROUTE_FACTS=none` launches it without facts on purpose), because without facts every task runs on the strong tier. Restarts and reviews reuse the facts; a worker's checkpoint may change `specification` and `scope` (worker contract). What each fact means: hive-route ADOPTING.md §4, "Facts".

**Scorers and the reader** (table version 18). Two local models read each task's order text. Neither changes routing yet:
- `qwen-local` (Qwen 8B on `ollama.service`, port 11434) is the scorer, in shadow. When a fact is unknown, it estimates it.
- `kev-4b` (Kev-4B fine-tuned as the reader, run `~/opt/kev/runs/reader-ft-v1`, on `kev.service`, port 8009; hive-route rev 16) is the reader (hive-route ROUTING §4.8), in shadow. It reads all four facts on every attempt and logs `route.read`, so `hive-route report` shows where cos's `Route facts:` look too cheap or too costly.
  - The launcher marks cos as the writer of the facts (`ROUTE_WRITER` overrides it).
  - Kev is installed in `~/opt/kev`. CUDA graphs and the prefix cache are off so it stays under about 10 GB of GPU memory, next to Ollama. Any local process may call it.
  - The route's `weights` name the run `kev.service` serves (`--run`). They're in its pin, so a new run means: a new run name, `kev.service` and `weights` changed together, then requalify. vm2 reads through the gate, so it must change its own `weights` the same way and requalify.
  - It is qualified: run `hive-route reader-qualify deploy/route-table.yaml <hive-route>/fixtures/scorer/portable.jsonl --sources deploy/route-sources.yaml --log ~/work/1hive/route-log.jsonl` again after any change to the reader. Going `live` is a table change for the operator.

**Kev for vm2: `kev-gate`.** Ben's vm2 has no GPU, so it uses this host's Kev as its reader, through `tools/kev-gate.py` (user service `kev-gate.service`, on `127.0.0.1:8010`).
- **What it serves:** only `POST /v1/systemone` with a bearer key, forwarded to Kev on loopback.
- **Public URL:** Tailscale Funnel publishes the gate, and nothing else, at `https://omegahive-host.tail5833f.ts.net`: `tailscale funnel --bg 8010`, kept across restarts. vm2 needs no Tailscale. sshd and the other loopback services aren't exposed.
- **Its addresses aren't ours and aren't stable.** The Funnel name resolves to Tailscale's relay servers (IPv4 and IPv6), not to this host, and Tailscale moves them without notice: on 2026-10-25 they went from 209.177.145.x to 103.84.155.x. A hive that allowlists its outbound traffic must allow the name, or look it up again on a timer, never pin the addresses once. vm2 pinned them at service start, and its readings failed for two days until a restart (hive-route ADOPTING §10).
- **Key:** `~/.config/hive/kev-gate.key`, mode 600, which the operator hands to vm2. The gate keeps only its hash, in `kev-gate.sha256`.
- **Logs:** one line per request: time, status, sizes and seconds. Never the text.
- **Rotating the key:** write a new key and its hash, then restart the gate.
- **Stopping access:** `tailscale funnel --bg 8010 off`, or stop the gate.

Compare scorers with `hive-route scorer-eval deploy/route-table.yaml <hive-route>/fixtures/scorer/portable.jsonl --scorer <route>`.

**Review tiers.** A review runs at least at the author's tier (router rule F7). For a high-stakes task, the order can ask for more with a line `Review tier: strong`; hive-runtime's `launch-task.sh` passes it to the router as a hint, which can only raise the tier. The review-only route `sc-deepseek-v4` (standard) then can't take it.

**Canaries.** `canaries/reviews/` is 1-hive's own review suite (cases from past reviews with known verdicts); run it with `hive-route canary run deploy/route-table.yaml <route> --suite canaries/reviews --sources deploy/route-sources.yaml --log ~/work/1hive/route-log.jsonl`.
